# my_softlist

**AI-assisted Windows Workstation Management**

一个基于 YAML 的个人工作站软件与开发工具链管理模板。

`my_softlist` 不只是记录安装了哪些软件，而是尝试建立一套可持续维护的工作站管理流程：让 AI 协助完成软件盘点、工具链审计、目录规划、安装清单生成，以及新设备迁移。

通过一份结构化配置文件，让软件管理从零散的手动记录变成可追踪、可确认、可复用的工作流程。

## 核心功能

- **软件清单管理**：集中记录软件名称、用途、分类、安装方式、依赖关系和数据备份位置。
- **本机软件盘点**：支持从现有软件清单开始，也支持先识别本机已安装的软件，再生成清单草稿。
- **工具链审计**：检查软件维护状态、版本情况、重大缺陷，并寻找更合适的替代方案。
- **开发环境整合**：评估哪些开发工具可以交由统一的版本管理器安装和管理，减少重复管理工具与 PATH 混乱。
- **目录结构规划**：统一规划软件本体、缓存、项目工作区、安装包和备份目录。
- **安装清单生成**：根据软件依赖关系进行排序，生成有序的安装清单。
- **工作站迁移**：将软件清单和目录规划带到新设备，辅助重建工作环境。

## 设计原则

### 1. 配置与执行分离

YAML 文件负责描述工作站状态、管理规则和操作流程。

AI 根据配置提供分析、建议和清单，但不会擅自执行安装、卸载或修改系统。

### 2. 分阶段确认

整个流程采用阶段式管理：

每个阶段完成后，都需要用户明确确认，才能进入下一阶段。

用户可以随时回到指定阶段重新执行，后续阶段的确认状态也会随之失效。

### 3. 尽可能统一工具链

开发环境尽量由一个主管理工具负责。

例如，通过 `mise` 统一管理 Node.js、Rust、Bun 等开发工具，减少独立安装、环境变量和 PATH 配置的复杂度。

不适合统一管理的软件仍然独立安装，不强行整合。

### 4. 安全优先

- 本机软件识别采用只读方式。
- 默认只记录软件名称，不收集软件版本和旧安装路径。
- 不自动运行安装程序。
- 默认不下载软件，只有用户明确同意后才执行下载。
- 下载优先使用官方来源，并在官方提供校验值时进行校验。
- 不确定的信息标记为 `unknown`，不编造版本、来源和下载地址。
- 对包含账号、订阅或密钥的数据路径进行特别提醒。

### 5. 保留用户决策权

AI 可以提出软件替换、工具整合和目录调整建议，但不能自行决定最终方案。

所有涉及软件清单、目录结构和安装策略的修改，都需要用户确认。

## 工作流程

整个流程分为六个阶段：

| 阶段 | 内容 | 主要产出 |
|---|---|---|
| 0 | 预检 | 配置检查、能力确认、待补充信息 |
| 0.5 | 本机软件识别（可选） | 已安装软件清单草稿 |
| 1 | 软件与工具链审计 | 软件保留、移除、新增和替换建议 |
| 2 | 目录规划 | 软件、缓存、工作区及备份目录方案 |
| 3 | 安装清单 | 按依赖关系排序的安装清单 |
| 4 | 可选下载 | 经用户授权下载的安装包 |
| 5 | 完成 | 工作站配置流程结束 |

每个阶段都需要用户确认后继续。

## 配置文件结构

主要配置文件：

`workstation-template.yaml`

配置分为以下几个部分：

| 模块 | 作用 |
|---|---|
| `meta` | 模板版本、运行模式和当前流程状态 |
| `agent` | AI 的角色、行为约束和阶段流程 |
| `vars` | 软件、缓存、项目、下载和备份目录 |
| `policies` | 软件审计、目录规划、扫描和下载规则 |
| `software_defaults` | 软件条目的默认配置 |
| `software` | 实际的软件清单 |

### 软件条目

每个软件可以记录：

- `id`：软件唯一标识
- `name`：软件名称
- `note`：软件用途与身份说明
- `category`：软件分类
- `required`：是否必装
- `install_mode`：安装方式
- `path_policy`：安装路径策略
- `depends_on`：依赖的软件
- `managed_by`：负责管理该软件的工具
- `data_paths`：需要备份或迁移的数据位置
- `status`：审计后的处理建议

未填写的字段可以继承 `software_defaults` 中的默认值。

## 使用方法

### 1. 获取配置文件

下载仓库中的 `workstation-template.yaml`。

### 2. 选择工作模式

修改：

```yaml
meta:
  mode: from_list
```

支持两种模式：

- `from_list`：从自己维护的软件清单开始。
- `from_scan`：先识别本机已有软件，再生成软件清单草稿。

### 3. 配置目录

根据自己的磁盘情况修改：

```yaml
vars:
  APP_ROOT: "D:/Apps"
  CACHE_ROOT: "D:/Cache"
  WORKSPACE_ROOT: "D:/Workspaces"
  DOWNLOAD_ROOT: "D:/Downloads/installers"
  BACKUP_ROOT: "D:/Backup"
```

### 4. 配置软件清单

在 `software` 中添加、删除或调整软件条目。

### 5. 提交给 AI

将完整 YAML 文件交给支持文件读取和联网搜索的 AI。

要求 AI 严格遵循文件中的 `agent` 指令，按阶段执行。

如果需要从某个阶段重新开始，可以直接告诉 AI：

```text
回到阶段 1
```

## 注意事项

- 这是一个配置模板和 AI 工作流程规范，不是独立运行的 Windows 软件。
- 本机软件扫描需要 AI 具备本机访问能力；不具备时，可以通过模板提供的 PowerShell 只读命令手动获取软件名称。
- 软件版本、维护状态和下载链接需要联网核实。
- 下载和安装是两个独立环节。即使下载完成，也不会自动运行安装程序。
- 迁移前应单独备份重要应用数据。尤其注意聊天记录、笔记工作空间、SSH 密钥、代理订阅等数据。
- 使用前应检查配置中的磁盘盘符和可用空间。

## 项目目标

希望通过结构化配置与 AI 协作，让个人工作站拥有一份持续更新的软件资产清单和环境管理方案。

无论是整理现有电脑、优化开发工具链，还是迁移到一台新设备，都可以从同一份配置出发，逐步完成规划与重建。
